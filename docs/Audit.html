wpo-reference: audit

20 Nov 2026 · A check of the mock WPO project against the team's email and the NaviStorm wireframes: what was asked, what was built, how we know it works, and what is still left. Written in plain words; a short glossary is at the end.

In one paragraph. Everything the email asked for is built and working. The project has six pretend systems, a tool layer (MCP) in front of them, and five AI agents that use only that tool layer. One command starts it all. When NaviStorm reads the project, it draws exactly the picture the email asks for: 1 orchestrator, 5 agents, 11 MCP tools, 6 systems, 18 edges, and it says for every box and line how it knows. A final code review (section 5b) found and fixed one serious problem and several smaller ones. For the demo, run NaviStorm from branch wpo-demo: m4-experiments plus the small NaviStorm fixes this project needed.

1. What was built

A pretend version of a Workforce Optimization product: the kind of system that plans who works which shift at which site. Nothing in it talks to a real company system. It lives in its own folder, ~/Desktop/wpo-reference, with its own git history.

PartWhat it is, simplyHow many
Stand-in systemsTiny web services that pretend to be SAP, Workday, the manufacturing system (MES), the training system (LMS), the NVIDIA solver (cuOpt) and Microsoft Teams. They always give the same fixed answers.6
Pretend data14 sites, 56 workers, 12 absences, 28 production lines, 84 training records, 4 rules, last night's roster. Made-up names.7 files
MCP serversThe "tool layer" in front of each stand-in. Agents ask a tool for something; the tool asks the stand-in. Tools that change data are labelled as such.8 servers, 11 tools (3 that write)
Agentsforecast_demand, optimize_roster, compliance, writeback (run in that order by a supervisor), and manager_copilot (on its own).5
PackagingOne Docker image and one Compose file. make up starts everything; only the agents can be reached from outside.15 services
ChecksAutomatic tests, a full start-to-finish test in Docker, and a script that asks NaviStorm's own scanner to read the project and compares the result with the expected picture.83 tests + 22 topology checks

How a nightly roster runs

Supervisor→ 1 · forecast_demand
plan, lines, absences + AI→ 2 · optimize_roster
workers, training, solver→ 3 · compliance
rules, training→ pass → 4 · writeback
Workday, SAP, Teams

If compliance fails, the roster goes back to the optimizer (at most 3 times, then the run stops). The manager copilot is separate: a manager asks a question, it reads the last published roster and answers.

Weaknesses left in on purpose

NaviStorm is a tool for breaking things on purpose, so the project needs weak spots for the demos to find. They are marked in the code with "do not fix".

#Weak spotWhy it matters in a demo
W1When Workday (or SAP, MES, or the AI) fails, the forecast agent retries forever, every second, and ignores the "please wait N seconds" signal (Retry-After)Asked for in the email. Under a Workday slowdown it floods Workday with calls: the first demo's finding
W2The optimizer waits until every one of the 14 sites has a forecastOne slow site holds up all sites (a finding in the Findings wireframe)
W3The copilot answers from the last roster without saying how old it isAfter a bad night, managers get yesterday's roster as if it were today's (a finding in the Findings wireframe)
W4When one write times out, writeback repeats all its writes, including those that already workedDuplicate schedules and confirmations: the "duplicate write" fault the journey wireframe lists for the write path

5b. Final code review

A separate reviewer read all of the project's code and the NaviStorm fixes, and ran real stand-ins and MCP servers to check behaviour. What it found, and what happened:

#FoundHow seriousNow
R1When a tool failed (e.g. Workday down), the error came back as if it were the answer. The forecast agent crashed instead of retrying, so the deliberate retry (W1), the first demo's whole point, never happened; with SAP down a run even reported "published"BlockerFixed: tool errors are now real errors. Checked live: Workday down → retries every second, then finishes
R2A whole MCP server down or hanging gave an error no retry rule caughtShould fixFixed: it now counts as a tool error ("did not answer" for a hang, so writeback retries it)
R3The AI client retried by itself and obeyed "wait N seconds", hiding W1; some AI errors (timeouts, 5xx) crashed the runShould fixFixed: the client no longer retries by itself; W1 catches every AI error
R4The guides pointed at a NaviStorm branch without M3/M4, and their check could pass on a checkout without the fixesShould fixFixed: use wpo-demo; the check now proves the fixes are in the checkout you run
R5The agents' port was open to the whole network, so anyone on the same Wi-Fi could start a rosterShould fixFixed: this machine only
R6A writeback retry re-sends writes that already workedShould fixKept on purpose and marked as weak spot W4 (it matches the wireframe's "duplicate write")
R7Business hours: a window ending at 24:00 closed a minute early; "24:00-06:00" crashed every requestSmallFixed; a bad setting now stops the service at start-up with a clear message
R8An unknown site reported "published"; a question without a site was answered for site-01; "site-100" read as "site-10"SmallFixed: 404 for an unknown site; the copilot asks which site
R9The NaviStorm "could not read" fix hid more than the one false noteSmallFixed in NaviStorm (commit 466771c) with a test
R10The weekly-hours rule could never triggerSmallFixed: the optimizer passes contract hours on to compliance

Also new: a system failure the agents do not retry (e.g. Teams refusing) now answers "502" with the system named, instead of a bare server error.

8. Glossary

WordMeans
Stand-in (stub)A fake version of a real system that gives fixed answers, so nothing real is touched
MCP, MCP server, toolA standard way for AI agents to use tools. An MCP server offers tools (e.g. "workday.absences"); the agent calls the tool, the tool talks to the system
Destructive hintA label on a tool saying it changes data (a write)
AgentA piece of the product that does one job, sometimes with AI (e.g. forecasting demand)
Orchestrator, supervisorThe part that runs the agents in the right order
Node, edgeA box in NaviStorm's picture (an agent, tool or system), and a line between two boxes (one calls the other)
TopologyNaviStorm's picture of all the boxes and lines
Source ("classified by")How NaviStorm knows a box or line is there: from the code, a tool's label (MCP manifest), the Docker Compose file, a known vendor's name, or traces from a real run
Sandbox runNaviStorm builds and runs the whole project in an isolated area, sends it traffic, and watches what happens
OTel tracesRecords of every call made during a run (OpenTelemetry), the most trusted source
Retry-AfterA system's way of saying "slow down, try again in N seconds"; ignoring it makes things worse
Fault injectionBreaking one thing on purpose (e.g. making Workday slow) to see whether the product copes
