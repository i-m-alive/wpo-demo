wpo-reference: analysis and implementation plan

20 Nov 2026 · A mock Workforce Optimization (WPO) product to point NaviStorm at for the demo. It is built from the team brief ("Build the reference repo"), the NaviStorm wireframes (screens 1–4, 6, 7, 10), and what NaviStorm already does on branch m2-faults / m3-safety. It lives in its own folder, ~/Desktop/wpo-reference, outside NaviStorm.

What we are building. A small, realistic system to break, that NaviStorm can draw with nothing configured by hand:

  • six FastAPI stand-ins for SAP S/4, Workday, MES, the learning system, NVIDIA cuOpt and Teams, each with canned answers;
  • one MCP server in front of each, plus policy and roster (8 servers, 11 tools; write tools marked destructiveHint);
  • LangGraph agents that reach those systems only through MCP: a supervisor graph running forecast → optimize → compliance → writeback, with a "fail" loop back to the optimizer, and a separate manager copilot graph;
  • one Docker Compose file and one image: docker compose up starts all 15 services.

The test it must pass. Pointed at this folder, NaviStorm's Topology shows 1 orchestrator, 5 agents, 11 MCP tools, 6 systems, 18 edges, and every node and edge says which source classified it (code, MCP manifest, Docker Compose, and after a sandbox run, OTel traces).

Not in scope (from the brief): latency benchmarking, load generation, performance measurement. Nothing talks to a real system.

Effort: about 4.5 developer-days. Your part: the decisions in section 4 (about 15 minutes), and the demo run-through at the end.

Status, 20 Nov 2026: implemented; all exit criteria hold. 62 tests pass; make smoke passes (15 services, both routes over real MCP); scripts/check_topology.py passes all 22 checks against NaviStorm's scanner; a NaviStorm sandbox run succeeded (9 of 9 scenarios, 15 of 15 services, about 2,500 spans, 6 model calls answered by the LLM stub) and every node and edge then lists "OTel traces". Walkthrough: DEMO.md.

Where the work differed from this plan:

  • WD6: the model setting is auto (Azure OpenAI whenever an endpoint and key are present, otherwise offline), not "offline unless WPO_LLM=azure". In a NaviStorm sandbox the endpoint points at NaviStorm's LLM stub, so the agents' model calls are real and traced there.
  • Reading MCP results: a real MCP server sends a list as one text block per item (plain strings unquoted). The Docker smoke test found that a single reader mis-read the 14 site ids; the agents now read lists and objects separately, and the test fakes answer in the real shape. NaviStorm's own stand-in fixture has the same latent bug (it is never run, so it does not show).
  • The retry delay is the integer constant FIXED_DELAY_S = 1 so NaviStorm reads "fixed 1 s"; with 1.0 it read "waits between attempts".
  • Two NaviStorm gaps found and fixed (plan section 12, 5.3), on NaviStorm branch wporef-scanner-n1, built in a separate worktree so the M4 work in progress was not touched: a3d8542 (a LangGraph node in its own module was also listed as "could not read") and 3cb5a00 (a Compose service with build: . and image: was left out of the sandbox plan). NaviStorm: 436 tests pass on that branch.
  • Training data has 84 rows (one per worker and line), not "one per worker".

Two things found during the analysis
  • NaviStorm scans test folders. It skips only .git, node_modules, .venv, dist, build and caches. A test that builds a fake MCP server or agent would add nodes to the topology. Rule for this repo: tests use the real modules through their routes and functions, and never define agents, MCP servers or clients of their own. Phase 5 proves the counts are the same with and without tests/.
  • NaviStorm's branch is busy. M4 work is in progress, uncommitted, on m3-safety. If Phase 5 finds a scanner gap, the fix goes on its own NaviStorm branch, never mixed into that work.

5.6 The model (WD6)

  • agents/llm.py has one factory. With AZURE_OPENAI_ENDPOINT and AZURE_OPENAI_API_KEY set, and WPO_LLM=azure, it returns AzureChatOpenAI (deployment from AZURE_OPENAI_DEPLOYMENT, default gpt-4o). Otherwise it returns an offline chat model with fixed answers ("Demand for site-03: 2 shifts on line A …").
  • Both are used the same way (llm.ainvoke), so the graph does not care. NaviStorm must count exactly one model (Azure OpenAI, gpt-4o) either way: a Phase 5 acceptance criterion.
  • Keys only in .env, which git ignores; .env.example holds names and blanks.
  • In NaviStorm's sandbox the Azure endpoint is sent to NaviStorm's LLM stub whatever the repo says (S6), so a sandbox run never reaches Azure.

9. Phase 2 · The MCP layer

0.75 dayRequirements R9, R10

2.1 Six servers in front of the stand-ins

  1. One file per server (sap_server.py …), literal FastMCP("sap", host="0.0.0.0", port=9000), streamable HTTP at /mcp, stateless, JSON answers.
  2. Each reads its stand-in's address from one variable (SAP_URL, default http://stub-sap:8000), uses httpx with a 10 s timeout, and raises an MCP tool error with a short message when the stand-in fails or times out.

2.2 Two internal servers

  1. policy_server.py (rules) and roster_server.py (store), serving data/policy_rules.json and data/roster_published.json. No stand-in behind them: they are not systems.

2.3 Annotations and types

  1. As in 5.4: ToolAnnotations(readOnlyHint=True) on reads, ToolAnnotations(destructiveHint=True) on the three writes; return types written out; a one-line docstring per tool saying what it supplies (the wireframe's "What it supplies").

2.4 Tests (tests/test_mcp_servers.py)

  1. For each server: its tool list (names, annotations, input schema), via the server object's own listing. No new servers are defined in tests.
  2. Calling each tool with the stand-in mocked by respx: the right method and path, the answer passed through; a 5xx or timeout becomes a tool error.
Acceptance criteria
  1. 8 servers expose exactly 11 tools with the names in 5.4.
  2. Exactly the three write tools carry destructiveHint: true; the other eight carry readOnlyHint: true.
  3. A failing or slow stand-in gives a tool error, never a crash.
  4. All MCP tests pass.

10. Phase 3 · Agents and orchestration

1.25 daysRequirements R10–R16

3.1 MCP client (agents/mcp_client.py)

  1. One MultiServerMCPClient with the 8 servers, each URL from its variable (SAP_MCP_URL …).
  2. tools_named("server.tool", ...) returns those tools, by their literal names (NaviStorm reads these; S1). data() turns a tool result into JSON.
  3. No other way to reach a system exists in agents/ (R10).

3.2 The model factory (agents/llm.py)

  1. As in 5.6; the offline model returns fixed, readable answers built from its input, so the demo shows sensible text.

3.3 forecast_demand (W1)

  1. Calls the three tools, then asks the model for demand per site from the results (one prompt for all sites the run covers).
  2. Wrapped in the deliberate retry: while True, fixed time.sleep(FIXED_DELAY_S), catching tool errors and RateLimitError, never reading Retry-After. The comment block above it says it is deliberate, what it demonstrates, and not to fix it.

3.4 optimize_roster (W2)

  1. Workers, training currency, then cuopt.solve for all sites in one payload. MAX_RETRIES = 2, MAX_ITER = 4, as in the stand-in fixture.

3.5 compliance and the conditional edge

  1. Reads the rules and training currency; checks the roster (the solver's empty roster passes, so a normal run goes straight through).
  2. add_conditional_edges("compliance", route, {"pass": "writeback", "fail": "optimize_roster"}); a rounds counter in the state ends the run as "rejected" after 3 rounds (WD10). No retry.
  3. A setting, WPO_FORCE_COMPLIANCE_FAIL=1, makes the check fail, to show the loop in a demo.

3.6 writeback

  1. Schedules, shift confirmation, notification; for _ in range(3) with continue on a timeout; returns {"published": true|false}.

3.7 The supervisor graph (agents/supervisor.py)

  1. The StateGraph of 5.5, compiled as supervisor. State: sites, forecast, roster, compliant, rounds, published.

3.8 The copilot graph (agents/manager_copilot.py, agents/hours.py)

  1. Its own StateGraph: START → manager_copilot → END, compiled as copilot.
  2. Reads roster.store for the site asked about, then asks the model. W3: the answer never mentions when the roster was published.
  3. hours.py: COPILOT_HOURS (default 07:00-19:00), COPILOT_TZ (default Europe/London); 00:00-24:00 means always open.

3.9 The API (agents/main.py)

  1. Routes of 5.5. /roster/run runs one site or all 14; /copilot/ask answers 423 with "The copilot answers between 07:00 and 19:00 (Europe/London)" outside hours.
  2. Errors come back as JSON with a plain message; nothing prints secrets.

3.10 Tests (tests/test_agents.py, test_graphs.py, test_api.py)

  1. Graphs: node names and order; the conditional edge's two targets; the copilot graph is separate.
  2. Each node with its tools replaced through the test's monkeypatch of tools_named (no fake servers or clients defined): which tools it asks for; W1 keeps retrying with a fixed delay and ignores a Retry-After value (time patched, stops after N tries by the test); optimizer gives up after 3 attempts; writeback retries a timeout twice; compliance fail → optimizer, ending after 3 rounds.
  3. API: both routes with the offline model; 423 outside hours; /healthz.
